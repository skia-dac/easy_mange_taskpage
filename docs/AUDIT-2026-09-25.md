## 2. Validation des saisies (« check on input full »)

### 2.1 Transverse

- **V1 — Critique.** `src/shared/ui/useSave.ts:22-23` : après `await action()`, `setErrors({})` est appelé. Tout écran qui fait `setErrors({...}); return;` *dans* `run` voit son erreur effacée immédiatement. Cas : `src/app/habits/checkpoint.tsx:114` (« abc » comme poids), `src/app/money/loan-form.tsx:66` (montant vide). **Fix** : lever `new ValidationError({ champ: 'clé' })` (`@/shared/validation`) au lieu de `setErrors`, ou faire vider les erreurs *avant* l'action.
- **V2 — Important.** `parseInput` (`shared/validation.ts:70-73`) recopie `issue.message` brut ; `FieldShell` fait `t(message)`. Toute règle zod sans `{ error: 'clé' }` affiche par ex. `Invalid input: expected number, received NaN`. Champs concernés : `exam.ts:19-21` (`durationMinutes` `.int()`), `:32` (`grade`), `:38` (`gradeMax`), `:40` (`coefficient`), `habit.ts:50` (`target` `.int()`/`.max(50)`), `:48` (`timesPerWeek` `.max(7)`). **Fix** : ajouter la clé sur chaque règle ; filet de sécurité dans `parseInput` : tout message qui ne commence pas par `validation.`/`money.`/`auth.` devient `validation.invalid` (clé à créer FR/EN).
- **V3 — Important.** Écrans hors `useSave` où une `ValidationError` devient « Une erreur est survenue » (popup générique) : note d'opération > 120 car. (`money/add.tsx:284`), sous-tâche > 120 (`SubtaskList.tsx:86-105`), catégorie d'argent > 30 (`money/settings.tsx:61-70`), note d'humeur > 500 (`MoodPicker.tsx:95`), contenu de note > 100 000 à l'autosave (`notes/[id].tsx:149`). **Fix** : `maxLength` aligné sur le schéma + `isValidationError(e)` pour afficher sous le champ.
- **V4 — Important.** `habits/form.tsx:228-234` : `unit` validé (20 max) mais sans `error=` ni `maxLength` → erreur muette, le bouton « semble ne rien faire ».
- **V5 — Important.** `noteCommands.ts:38-39` `saveNoteContent` écrit sans passer par `noteInputSchema` : la limite de 100 000 caractères ne s'applique qu'à la création.

### 2.2 Par écran (mineurs)

- `exams/form.tsx:92` : `replace(',', '.')` ne remplace que la première virgule ; `Number()` accepte `1e3`, `Infinity`. `gradeMax`/`coefficient` sans borne haute.
- `habits/form.tsx:233` : l'unité reste enregistrée quand l'objectif repasse à 1.
- `money/goal-form`, `recurring.ts:19-22` : montants sans borne haute (contrairement aux opérations) ; échéances passées acceptées.
- `money/loan-form.tsx:262`, `recurring-form.tsx:346` : `note` sans `maxLength` ni `error=`.
- `planning/slot-form` : `slot.ts:45-46` renvoie la clé `endAfterStart` (heure) pour une comparaison de **dates** → utiliser `untilAfterFrom`.
- `work/form`, `events/form` : `reminderAt` après l'échéance ou dans le passé accepté.
- `checkpoint.tsx` : date de point de suivi dans le futur acceptée.
- Pas de contrôle de doublon (matière, emploi du temps, catégories).
- `colorId`/`icon` = `z.string().min(1)` sur habitudes, créneaux, catégories (non restreints à la liste, contrairement aux matières).

### 2.3 Ce qui est bien

Helpers centralisés (`requiredText`, `optionalText`, `isoDate` via date-fns, `time`), flux uniforme `parseInput → ValidationError → useSave → FieldShell` (avec `accessibilityRole="alert"`), refinements croisés partout (fin > début, note ≤ barème, tontine, poids ou photo), `parseAmount` robuste + clavier d'argent qui bloque à la source, auth conforme (e-mail normalisé, mot de passe 8–72 lettre+chiffre, confirmation, codes Supabase mappés), réglages entièrement par listes fermées re-validées à l'écriture. Toutes les clés d'erreur existent en FR et EN. Aucune incohérence entre colonnes `NOT NULL` et champs optionnels.

## 4. Données, synchronisation, sécurité

### 4.1 Vérifié conforme

Migrations 1→15 consécutives, jamais modifiées (historique git), chacune en transaction ; `SYNCED_TABLES` = `BACKUP_TABLES` = tables serveur (26) ; RLS sur les 27 tables, bucket par utilisateur, `mysky_push` avec liste blanche et idempotence ; toutes les écritures par `write()`/outbox ; SQL paramétré (interpolations = noms de tables du code) ; `PRAGMA foreign_keys` + `defer_foreign_keys` à la réception ; cascades logiques complètes (habitude → logs, points, photos ; note → pièces jointes ; matière ; emploi du temps ; examen ; créneau ; catégories) ; photos de progression **exclues** de la sync fichiers et effacées par « Supprimer toutes mes données » ; aucun secret dans l'app ; session en SecureStore ; `allowBackup: false`.

### 4.3 Gestion des erreurs

- **E1 — Important.** 14 formulaires d'édition chargent avec `void getX().then(...)` sans `catch` : en cas d'échec, formulaire vide « comme neuf », l'enregistrement suivant écrase par des champs vides. Fix : `useLiveQuery` + état d'erreur, ou `.catch → showError + back()`.
- **E2 — Important.** `useLiveQuery.error` n'est lu par **aucun écran** : une lecture qui échoue affiche « Rien à faire ». Fix : bannière `errors.loadFailed` dans `Screen`.
- **E3 — Important.** `AccountGate.tsx:18` `void claimLocalData()` sans `catch` : la sync peut ne jamais démarrer sans le dire.
- Mineurs : `LockGate.tsx:66` **fail-open** si la lecture du réglage échoue ; `settings.tsx:111`, `useNotifications.ts:65`, `widgets/sync.ts:59,67` sans `catch` ; onboarding : échec d'enregistrement des espaces seulement journalisé ; `syncFiles` avale les échecs par fichier.

## 5. Points forts (à préserver)

1. Écritures transactionnelles + outbox dans la même transaction, `softDelete` universel, conflits conservés (`sync_conflicts`), schéma serveur **généré** et vérifié sur un vrai Postgres en CI.
2. Sécurité : RLS partout, `service_role` seulement dans l'Edge Function, PKCE, SecureStore découpé, garde `..` sur les chemins, échappement HTML, aucune donnée personnelle dans les logs, photos de progression jamais envoyées.
3. Kit UI cohérent, couleurs 100 % par tokens (ESLint), contraste testé, sombre partout ; accessibilité soignée.
4. Validation : flux unique et clair, refinements croisés, `parseAmount` robuste, auth conforme.
5. Local-first réactif (`useLiveQuery`), notes en autosave avec statut, confirmations contextuelles, `ErrorBoundary` avec « Réessayer ».
6. i18n : aucune chaîne brute, dates via `Intl`, parité FR/EN et clés utilisées testées.
7. Espaces : filtrage centralisé, données jamais modifiées quand un espace est coupé.
